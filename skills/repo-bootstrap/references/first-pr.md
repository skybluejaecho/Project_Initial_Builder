# 첫 작업 예시: 프로젝트 주제 후보 비교

소규모 팀이 `main`으로 PR을 보내고 작성자 외 1명 승인 후 작성자가 머지하기로 한 경우의 예시다. 대상 프로젝트에는 팀의 실제 브랜치·커밋·리뷰 규칙에 맞춰 짧게 적는다. 개인 프로젝트라면 외부 승인 대신 자기 점검을 사용한다.

**시작점:** 로컬과 원격이 모두 비었다면 팀원이 Git 저장소를 초기화하고 협업 문서만 첫 커밋으로 만든 뒤 빈 원격에 연결해 기준 브랜치를 푸시한다. 원격에 이미 팀 이력이 있다면 그 기준 브랜치를 받아 시작한다. 기존 팀의 직접 푸시 금지·리뷰 규칙을 그대로 따르고 별도 초기 이력을 만들지 않는다. 아래 비교표는 기준 브랜치가 준비된 다음 작업 브랜치에서 작성해야 첫 PR의 변경으로 보인다.

1. **작업 요청** — 목적: 다음 회의에서 주제를 고른다. 할 일: 후보 3개의 대상 사용자·문제·구현 난이도를 비교한다. 완료 조건: 세 후보를 같은 기준으로 비교한 표가 있고 남은 질문을 적었다. 주제의 최종 확정은 다음 회의에서 한다.
2. **분기와 커밋** — 원격 저장소에 기준 브랜치와 첫 커밋이 준비된 뒤 `main`에서 `docs/topic-options`로 분기한다. 비교표를 작성하고 `docs: 프로젝트 주제 후보 비교`로 커밋한다.
3. **첫 PR** — 작업 브랜치를 푸시한 뒤 `docs/topic-options → main`으로 PR을 연다. 목적은 “회의 전에 같은 기준으로 후보를 비교하기”, 변경은 “후보 비교표 추가”로 적는다. 표를 직접 확인했다면 “세 후보 모두 세 기준에 값이 있다. 난이도는 추정이어서 팀 확인이 필요하다”처럼 확인한 사실과 남은 질문을 나눈다.
4. **리뷰와 머지** — 리뷰어는 비교표가 완료 조건을 충족하는지 판단한다. 누락된 기준이 있다면 작성을 요청하고 작성자가 보완한다. 승인 후 작성자가 머지한다.

빈 폴더에서는 위 절차를 앞으로 할 일로 안내한다. 예시용 비교표·이슈·브랜치를 만들거나 검증·승인·머지가 이미 끝났다고 기록하지 않는다.
