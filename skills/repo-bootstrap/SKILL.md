# Repo Bootstrap

기존 프로젝트의 사실과 팀 합의를 바탕으로 최소한의 협업 문서를 준비한다. 현재 대화에서 지정한 대상 프로젝트를 작업하며, 설치된 스킬 폴더를 대상 프로젝트로 착각하지 않는다. 사용자와 기존 문서의 언어를 따른다.

## 범위와 동작 선택

- **설정·보완:** 사용자가 요청한 항목만 생성하거나 최소 수정한다. 포괄적인 협업 초기 설정 요청에는 협업 규칙, PR 양식, Codex·Claude 연결을 포함한다. 일부만 요청하면 나머지는 편집하지 않는다.
- **점검:** 읽기와 보고만 수행한다. 파일 생성·수정, 설치, 포맷팅, 테스트·빌드 실행, Git 상태 변경을 하지 않는다. 보고서도 별도 저장 요청이 없으면 대화에만 남긴다.
- 요청이 단순 진단인지 편집인지 불명확하면 먼저 읽기 전용으로 진단하고, 편집이 필요한 항목과 선택을 제시한다.

기본 편집 대상은 기존 협업 규칙 문서(없으면 `CONTRIBUTING.md`), 루트 `AGENTS.md`, Claude 연결 파일, 기존 PR 템플릿(없으면 `.github/pull_request_template.md`)이다. CI, 린터, `.gitignore`, Git hook, 브랜치 보호, 원격 저장소 설정, 스킬 관리는 이 스킬의 범위 밖이다. 브랜치 생성·커밋·푸시는 초기 설정에 포함하지 않으며, 사용자가 따로 요청한 경우에만 그 요청 범위로 수행한다.

## 1. 기존 근거 확인

1. 대상 경로와 저장소 루트를 확인한다. Git 저장소가 아니어도 지정 폴더에서 문서 준비는 가능하며, Git 초기화나 원격 저장소 생성을 추론하지 않는다. Git 저장소에서는 현재 변경 사항과 아직 첫 커밋이 없는 경우도 확인한다.
2. 적용되는 프로젝트 지침과 기존 `AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md`, `.claude/CLAUDE.md`, `.claude/AGENTS.md`를 확인한다. `.claude/AGENTS.md`는 Claude에서 프로젝트 지침으로 자동 로딩될 수 있으므로 단순한 하위 폴더 규칙으로 분류하지 않는다. 개인 지침·로컬 전용 내용은 공유 문서에 복사하지 않는다. 일반 하위 지침은 범위만 파악하고 루트로 끌어올리지 않는다.
3. README와 기여 안내에서 팀 규칙의 기존 원본을 찾는다. PR 템플릿은 루트, `docs/`, `.github/`의 대소문자 변형 및 `PULL_REQUEST_TEMPLATE/`의 복수 템플릿도 확인한다. 기존 양식이 있으면 새 기본 양식을 추가하지 않는다.
4. 패키지·빌드 설정, lockfile, CI가 있으면 실행·검증 명령의 근거를 확인한다. 여러 lockfile이나 문서 불일치는 충돌 후보로 보고한다. 주제·스택이 미정이어도 협업 설정을 진행한다. 스택 선택을 요구하거나 없는 명령·앱 구조를 만들지 않는다.

확인된 사실, 사용자가 합의한 규칙, 미확인 사항을 구분한다. 최신 사용자 지시를 반영하되, 모순되는 기존 문서를 조용히 무시하지 말고 관련 변경을 설명한다. 기본 브랜치명이나 Git 이력의 패턴만으로 팀 정책을 확정하지 않는다.

## 2. 필요한 선택만 확인

기존 규칙과 대화에 근거가 있으면 다시 확인하지 않는다. 미합의 정책이 실제 결과에 영향을 줄 때만 질문을 묶어서 제시한다. 빈 항목을 채우려고 브랜치 전략·리뷰 인원·커밋 언어를 발명하지 않는다.

전반적인 협업 설정에서는 분기 기준과 PR 대상, 작업 완료 기준, 승인 조건과 머지 담당을 정한다. 기존 문서나 요청만으로 결정되지 않을 때는 개인/팀 여부와 별도 통합 브랜치 필요 여부 등 결과를 바꾸는 질문만 묶어 확인한다. 기본안 **제안** 요청은 대화로 답하고, 기본안 **적용**을 맡긴 경우에만 다음을 프로젝트에 맞춰 기록한다.

- 브랜치: 기준 브랜치에서 `feat/설명`, `fix/설명`, `docs/설명`으로 분기하고 같은 기준 브랜치로 PR을 연다. 빈 폴더에서는 `main`을 **예정 이름**으로 제안한다. 기존 팀이 `develop` 등 다른 통합 브랜치나 명명법을 사용하면 그 규칙을 따른다.
- 커밋 메시지: `feat: 설명`, `fix: 설명`, `docs: 설명`.
- 작업 요청: 목적·할 일·확인 가능한 완료 조건을 적는다. 완료 조건은 PR에서 결과물과 확인 근거로 판단할 수 있어야 한다. 코드가 없으면 문서 비교나 합의 결과로도 확인할 수 있다.
- PR: 변경 목적, 주요 변경, 검증 결과(미실행 시 이유), 관련 이슈(있는 경우). 이슈 템플릿이나 이슈 생성은 필요하지 않다.
- 리뷰·머지: 개인은 완료 조건을 스스로 확인한 뒤 머지한다. 소규모 팀 기본안은 작성자 외 1명 리뷰, 수정 요청 반영 후 승인되면 작성자가 머지하는 방식이다. 팀 규칙이 정한 인원·담당자·머지 방식이 있으면 유지한다. 이 문서 합의를 GitHub의 강제 설정으로 보고하지 않는다.

이 기본안은 추천안이며 기존 규칙보다 우선하지 않는다. `develop` 브랜치, 이슈 번호 필수화, 커밋 메시지 검사 도구를 추가하지 않는다. 충돌로 결정이 필요한 부분만 보류하고 독립적으로 처리할 수 있는 요청은 진행한다.

## 3. 설정·보완

점검 요청에서는 이 단계를 건너뛴다. 기존 파일을 덮어쓰는 일괄 템플릿 복사를 하지 않는다. 사용자 작성 문단·주석·관련 없는 로컬 변경을 보존하고 기존 줄바꿈과 문서 구조를 가능한 한 유지한다. 심볼릭 링크는 일반 파일로 대체하거나 경계를 넘어 편집하지 말고 대상과 범위를 먼저 확인한다.

### 협업 규칙

기존 원본 문서를 우선 사용한다. 없을 때만 `CONTRIBUTING.md`를 만든다. 전반적인 협업 설정에는 선택된 규칙으로 **첫 작업 요청 → 분기·커밋 → PR 대상·검증 → 리뷰·머지**를 따라갈 수 있는 짧은 예시 하나를 같은 문서에 둔다. 이미 동등한 예시가 있으면 유지한다. 기준 브랜치의 첫 커밋과 원격이 있어야 실제 PR을 열 수 있다는 전제와 현재 상태를 구분한다. 예시 작성은 Git 초기화, 커밋, 이슈·PR 개설, 승인을 실행하라는 요청이 아니다. PR 양식만 요청한 경우 등 부분 요청에 협업 예시를 덧붙이지 않는다.

기존 린터·포맷터는 설정 위치를 안내하고 세부 옵션을 중복 작성하지 않는다.

### PR 양식

기존 양식이 충분하면 유지한다. 누락을 보완할 때도 사용자 지정 체크리스트와 복수 양식 구조를 보존한다. 양식이 없을 때만 [PR 템플릿](assets/pull_request_template.md)을 대상 언어에 맞춰 사용한다. 관련 이슈는 선택 사항이며 검증을 실행하지 못한 경우 이유를 적을 수 있게 한다.

### Codex·Claude 공통 지침

이 항목을 작업할 때 [호환성 참고](references/compatibility.md)를 읽는다.

- 공통 AI 작업 지침은 루트 `AGENTS.md`에 둔다. 이미 다른 공통 문서가 원본이면 중복 대신 그 문서를 언제 읽어야 하는지 명시한다.
- 프로젝트 목적, 확인된 작업·검증 명령, 실제 프로젝트 고유 규칙, 필요한 문서 경로만 담는다. 명령을 모르면 생략하거나 미확인으로 표시하며 만들어내지 않는다.
- 브랜치·커밋·PR 작업 전에 기존 협업 규칙 원본을 읽도록 안내한다. 일반 Markdown 링크는 자동 가져오기를 보장하지 않는다.
- 기존 Claude 파일에서 범위가 동일한 공통 지침만 옮긴다. 옮기기 전후 의미가 보존되는지 확인하고 해당 문단만 정리한다. 이동한 문단의 상대 경로는 새 위치 기준으로 확인한다. Claude 전용 문법·내용은 남긴다. 의미가 불명확하거나 상충하면 해당 문단을 보존하고 확인한다.
- Claude 연결 파일을 새로 만들기 전에 기존 자동 로딩 경로를 확인한다. 새 `CLAUDE.md`로 기존 `.claude/AGENTS.md`의 자동 로딩이 중단될 수 있으면, 원문과 위치를 보존하고 새 연결에서도 그 내용을 가져오도록 한다. 파일 해시가 같다는 이유만으로 적용 범위가 보존됐다고 판단하지 않는다. 구체적인 연결 예시는 호환성 참고를 따른다.
- 기존 Claude 연결 파일에 올바른 상대 경로의 `@` 가져오기를 한 번만 추가한다. 연결이 이미 동작하면 그대로 둔다. 별도 기존 로딩 경로가 없고 파일도 없을 때의 최소 연결은 루트 `CLAUDE.md`의 `@AGENTS.md`이다. 기존 가져오기를 포함해 중복·순환과 충돌을 확인하고, 보존 여부가 불명확하면 해당 연결 변경을 보류한다.
- 루트 override, 여러 Claude 진입 파일, 순환 참조 등으로 활성 지침이 불명확하면 해당 연결을 완료로 표시하지 않는다. 사용자 설정을 자동 변경하거나 하위 지침을 일괄 변환하지 않는다.

같은 요청과 근거로 재실행했을 때 변경이 필요 없다면 파일을 쓰지 않는다. 생성 시각, 실행 이력, 자동 관리 표식을 추가해서 불필요한 diff를 만들지 않는다.

## 4. 점검과 결과 보고

요청 범위에서 다음을 확인한다.

- 문서 참조 경로와 Claude 가져오기 대상이 존재하고, 가져오기 순환이나 중복 연결이 없는지. 연결 전 자동 로딩되던 프로젝트 지침이 연결 후에도 도달 가능한지.
- 안내한 명령이 프로젝트 설정·문서에 근거하며 실행 위치가 맞는지. 정의 확인과 실제 실행 성공을 구분한다.
- 기존 문단·양식·전용 지침과 관련 없는 변경을 보존했는지. 변경 전후를 비교하고, 변경이 없으면 없다고 보고한다.
- 점검 요청에서는 작업 전후 파일 상태가 동일한지 확인한다. 문제를 발견해도 자동 수정하지 않는다.

검증을 위해 기본적으로 패키지 설치나 앱 테스트를 실행하지 않는다. 사용자가 실행 검증도 요청했다면 그 범위에서 수행하고 결과를 구분한다. 에이전트가 파일을 실제 로딩했다는 근거가 없으면 로딩 성공이나 정책 강제를 주장하지 않는다.

최종 응답에는 변경·유지한 파일과 이유, 확인 결과, 미확인 사항 또는 보류한 충돌만 간결하게 담는다. 점검 결과에는 문제의 파일과 근거를 제시하고 확정 오류와 의미상 충돌 후보를 구분한다. 사용자가 후속 조치를 해야 할 때만 구체적인 다음 행동을 안내한다.
